## Architecture (INSTRUCTIONS.md / ARCHITECTURE.md)
- AI Automation Master Agent orchestrates six employee agents: Agent Management, Version Management, API & Integration Management, Tenant Management, Permissions & Policies Management, Monitoring & Audit.
- Business-module agents (AR Agent first, then Finance Reconciliation) sit alongside the employee agents, each coordinating its own specialized sub-agents.
- Golden rule, applies to every sub-agent design: AI reads/drafts/classifies/prioritizes. Deterministic policy code calculates/decides/executes. Humans approve high-risk actions.
- AR Agent is an orchestrator, not a doer — it routes to 7 sub-agents (Invoice Delivery & Validation, Cash Application, Collections & Dunning, Dispute & Deduction, Credit Risk, Customer Inbox, AR Reporting & Forecast). Each is specified with explicit Deterministic / AI-assisted / Approval-gate columns — reuse that column structure for any new sub-agent.

## Deployment model (CONTEXT.md)
- Not pure multi-tenant SaaS — hybrid, closer to Datadog agent / Fivetran connector: a thin ERP-specific connector runs as an OS background service at the customer site (Windows Service / systemd); all AI reasoning (Master Agent, AR Agent, sub-agents, policy engine) stays centralized in the Console.
- Connector is outbound-only, always — never opens an inbound port. This is what makes it firewall-approvable at customer sites running legacy on-prem ERPs (Oracle EBS 10.2.8, QuickBooks Desktop) with no exception request. Kept as a `connectivity_mode` config value, not hardcoded, in case one tenant ever genuinely needs otherwise.
- Version fingerprinting is first-class, not an afterthought: every installation record carries erp_type/version, connector_module/version, ar_agent_version, sub_agent_versions, policy_config_version. `error_events` deliberately denormalizes this whole fingerprint onto every row so "show me every error on EBS 10.2.8 + connector v1.4.2" is one indexed query, not a five-table join.
- Each ERP is a pluggable adapter with a declared support status (alpha/beta/stable) and known-issues log — a living compatibility matrix, not hardcoded per-ERP branching.

## Registration & licensing flow (installation-registration-design.md)
- Lead capture (marketing site email) and installer self-report are deliberately separate concerns: email = identity & distribution; installer auto-detect = technical truth for the version matrix. Don't let one do the other's job — manual/email-reported versions are too imprecise for error correlation.
- Installer Step 0 = security & data-use notice ("we never store your passwords" + why the exact version matters), shown before any data is collected. `acknowledged_security_notice` is timestamped and enforced server-side — `/v1/registrations` rejects the request without it.
- Auto-detect ERP version first (registry/config/DB probe); fall back to asking; if even the customer doesn't know the patch level, accept major-version-only (e.g. "10.2.x"), set `erp_version_precision=major_only` + `needs_version_follow_up=true`, and surface it as a Console worklist for later follow-up — never block installation over a patch number.
- Token pattern: short-lived access token (1h, sent on every call) + longer-lived refresh token (30d, stored more carefully), rotated on every refresh use so a captured old refresh token can't be replayed. The background connector daemon — not the installer — owns silently refreshing before expiry.
- License expiry is a hard stop, not degraded/read-only: `connector_should_run` flips to `false` in the entitlements response the moment `license_status` hits `expired`. An hourly license-watcher job sends up to 3 renewal reminders on configurable day-thresholds beforehand (CCing the owner), idempotent via `renewal_reminders_sent`, reset to 0 on successful payment.

## Code scaffold status
- `console_registration_api.py` — FastAPI + asyncpg against real Postgres now (was in-memory dicts until 2026-09-08). Schema in `deploy/schema.sql`, applied automatically only on the `db` container's *first* creation (no migration tool yet — editing schema.sql later does nothing to a running deployment). Two disclosed deviations from installation-registration-design.md's data model, both commented in schema.sql: a `signup_codes` table (the doc doesn't specify how the one-time code itself is stored) and no `token_id` column on `installations` (a `credentials` table keyed 1:1 by `installation_id` makes that column redundant). Tokens are stored as sha256 hashes, never raw. One behavior change from the in-memory version: refreshing now invalidates the *previous* access token immediately (single active-credential-per-installation model) rather than letting it ride out its own TTL — harmless in practice since `connector_daemon.py` only refreshes at/after expiry anyway, but worth knowing if something else ever calls `/v1/token/refresh` opportunistically. `run_license_watcher()` is invoked standalone via `python console_registration_api.py` (its `__main__` block) — that's what the hourly cron entry in DEPLOY.md calls, sharing the same `DATABASE_URL` as the running API container via `docker compose exec`. Auth, rate limiting, and the billing webhook are still stubbed with TODOs.
- Postgres password lives in `deploy/.env` (gitignored, `deploy/.env.example` documents the shape) — generated directly on the droplet via `openssl rand`, never passed through chat in plaintext.
- Recreating just the `api` container (e.g. `docker compose up -d --build api`) leaves nginx pointing at the old container's now-dead internal IP — nginx resolves the `api` upstream hostname once at its own startup and doesn't notice a peer container was recreated. Fix is `docker compose restart nginx` right after. Symptom: 502 Bad Gateway with everything else looking healthy.
- `installer_skeleton.py` — `detect_erp()` is a pluggable-detector interface (add one function per new ERP, e.g. Oracle Fusion Cloud/NetSuite/SAP later, without touching the rest of the flow); token storage is a plaintext-JSON placeholder that must move to an OS secret store (Windows DPAPI/Credential Manager, Linux `keyring`) before shipping.
- `connector_daemon.py` — built. Loads the token pair the installer stored, runs the heartbeat loop, proactively refreshes the access token ~5 min before its 1h TTL (falls back to a reactive refresh on a mid-request 401), and halts all sub-agent sync the instant `connector_should_run` is false — while continuing to heartbeat so it notices a renewal without a reinstall. A `ReregistrationRequired` exception stops the daemon outright if the refresh token itself is rejected — that state needs a human to re-run the installer, not a retry loop.

- **Customer Inbox approval-resolution UI built (2026-09-08)** — the first (and, deliberately, only) place in this project where a human can actually resolve an `approval_queue` entry rather than watch it sit in `pending` forever. - **Generic approval-resolution built for all remaining action types (2026-09-08)** — `POST /v1/admin/approval-queue/{approval_id}/resolve` (`action: approve|reject`), covering the 8 action types Customer Inbox's dedicated flow doesn't: `dunning_activation`, `final_demand_letter`, `credit_memo`, `write_off`, `credit_hold`, `credit_release`, `credit_limit_change`, `cash_application_match`, `unidentified_cash`. Each has a genuinely different downstream effect on approval — a single "flip the status" endpoint would have been actively misleading (clicking Approve on a `dunning_activation` while the sequence stayed stuck in `pending_activation` forever, having sent nothing): (1) `dunning_activation`/`final_demand_letter` approve → `dunning_sequences` goes `active` at the gated step and **reuses `ar_agent._send_dunning_email()` directly** (imported into `console_registration_api.py`) so the actual email queues through the exact same outbox path, not a duplicated send routine; reject → a new terminal `dunning_sequences.status = 'rejected'` (a decision, not a deferral back to pending).
